# Quarantine Rollback on Failed From-Scratch Runs

## Problem Frame

`verify --from-scratch` quarantines derived/output/temp artifacts, runs the pipeline, then
returns — regardless of the pipeline's exit code. If the pipeline fails (non-zero exit), the
artifacts remain quarantined and are not restored. The project is left in a broken intermediate
state: source code is intact but outputs are missing. This is a correctness hole, not a
missing feature.

## Requirements

- R1. When `verify --from-scratch` runs and the pipeline subprocess exits with a non-zero return
  code, all quarantined artifacts are automatically restored to their original locations before
  `verify_project` returns. This is the default behavior.
- R2. Before restoring quarantined artifacts, any files already regenerated by the failed pipeline
  are deleted. This prevents partial/corrupt outputs from mixing with the restored originals.
- R3. After a successful pipeline run (zero exit code), the quarantine directory is deleted.
  Successful runs produce clean outputs; the quarantine dir is no longer needed.
- R4. A `--no-rollback` flag on `verify --from-scratch` skips automatic rollback on failure,
  leaving the project in its post-failure state. Intended for debugging (inspect partial
  outputs). The CLI prints a warning when `--no-rollback` is used: `Warning: rollback disabled.
  Project may be left in a broken state on pipeline failure.`
- R5. A new `restore-quarantine` CLI command restores artifacts from a specific quarantine
  directory: `econharness restore-quarantine [--path .] [--quarantine-dir <timestamp>]`.
  If `--quarantine-dir` is omitted, the command lists available quarantine directories
  (by timestamp) and exits with a message asking the user to specify one.
- R6. `restore-quarantine` deletes the quarantine directory after a successful restore.
- R7. `VerifyResult` includes a `rolled_back: bool` field indicating whether an automatic
  rollback occurred. The CLI prints this clearly: `Pipeline failed — artifacts restored from
  quarantine.`

## Success Criteria

- Running `verify --from-scratch` with a deliberately broken pipeline command leaves the project
  in its original state (all artifacts present), not in a broken intermediate state.
- `VerifyResult.rolled_back` is `True` when automatic rollback occurred.
- `restore-quarantine --list` (or with no `--quarantine-dir`) shows available quarantine dirs.

## Scope Boundaries

- Rollback is only for `--from-scratch` runs. `verify` without `--from-scratch` does not
  quarantine anything and is unaffected.
- No rollback for `check-clean-tree` failures — that check is a post-condition assertion, not
  a state-mutating operation.
- No automatic cleanup of old (unrestored) quarantine directories beyond the success case in R3.
  Stale quarantine dirs from prior failed runs (pre-fix) are left for the user or
  `restore-quarantine` to handle.

## Key Decisions

- **Always rollback on non-zero exit**: Any pipeline failure rolls back. Partial outputs from a
  failed build are unreliable and potentially corrupt — restoring to a known-good state is
  safer than preserving partial progress.
- **`--no-rollback` escape hatch**: Debugging requires inspecting partial outputs. The flag
  provides this without making dangerous behavior the default.
- **Delete quarantine dir on success**: A successful run means all expected artifacts were
  regenerated. Keeping the quarantine dir would waste disk space and create confusion.
